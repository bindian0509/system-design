Three Architectural Approaches

Choose the architecture that best fits the notification service requirements

A

Monolithic Notification Service

Single service handles all channels (SMS, Email, Push) with direct provider SDK calls inline. Quota and dedup logic lives inside the same process.

Pros

  • Simple to build and deploy
  • Easy to debug
  • Low operational overhead

Cons

  • Cannot scale SMS vs Email independently
  • One channel's slowness blocks others
  • 500M+/day will bottleneck fast
  • No buffering — spikes hit providers directly
B

Hub-and-Spoke with Channel Workers ✦ Recommended

Central Notification API handles auth, quota enforcement, deduplication, and priority routing. It enqueues to an internal priority queue. Separate worker services (SMS Worker, Email Worker, Push Worker) consume and dispatch to providers — each scales independently.

Pros

  • Each channel scales independently
  • Internal queue absorbs traffic spikes
  • Clear separation of concerns
  • Retry logic isolated per channel
  • Quota/dedup enforced at hub before queuing

Cons

  • More components to operate vs monolith
  • Adds internal queue (Kafka/Redis Streams)
C

Full Event-Driven Pipeline

REST API is just a thin gateway that publishes to Kafka topics per priority tier. Separate consumer groups handle each priority × channel combination with full fan-out. Maximum decoupling and throughput.

Pros

  • Maximum throughput and decoupling
  • Replay and audit built into Kafka
  • Natural backpressure per priority

Cons

  • High operational complexity (9+ consumer groups)
  • Quota enforcement harder across distributed consumers
  • Deduplication needs shared state (Redis) accessible by all consumers
  • Overkill given REST API integration choice
