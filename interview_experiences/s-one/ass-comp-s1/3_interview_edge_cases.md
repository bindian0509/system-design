# Singularity Health Center: Interview Edge Cases & Trick Questions

As a Senior Engineering Manager candidate, the interviewers will test your depth by throwing operational nightmares and edge cases at your design. Here is a curated list of trick questions and how to architecturally defend against them.

## 1. The "Thundering Herd" Problem
**Interviewer:** "AWS `us-east-1` has an outage. 500,000 agents lose connectivity for an hour. When AWS comes back, all 500k agents try to reconnect and send an hour's worth of buffered telemetry at the exact same second. What happens to your system?"

**The Trap:** If you don't have backpressure, your API Gateway will crash (OOM), or Kafka will become a massive bottleneck, taking down the entire cluster.

**The Solution:**
1.  **Agent-Side Jitter & Exponential Backoff:** Agents must never retry at the exact same time. They should implement randomized jitter (e.g., retry in `base_time * 2^attempt + random(0, 10) seconds`).
2.  **API Gateway Rate Limiting & Load Shedding:** The Go Gateway must enforce rate limits per tenant/IP. If it's overwhelmed, it should return `HTTP 429 Too Many Requests` or `HTTP 503 Service Unavailable`. It is better to drop telemetry temporarily than to crash the ingestion layer.
3.  **Kafka Backpressure:** Ensure the Gateway uses asynchronous publishing with bounded memory buffers so it doesn't block indefinitely if Kafka is slow.

## 2. The "Hot Partition" Problem
**Interviewer:** "You chose to partition Kafka by `tenant_id`. Tenant A is a massive enterprise with 2 million endpoints. Tenant B is a small business with 50 endpoints. What happens?"

**The Trap:** Partitioning solely by `tenant_id` means all 2 million events for Tenant A go to a single Kafka partition, handled by a single broker and a single Flink consumer thread. This creates a "hot partition" that will lag infinitely, while other partitions sit idle.

**The Solution:**
*   Partition by a composite key: `Hash(tenant_id + agent_id) % num_partitions`.
*   This guarantees that all events for a *specific agent* are processed in order (which is required for stateful anomaly detection like tampering on/off), but spreads the load of a massive tenant evenly across the entire Kafka cluster.

## 3. Clock Skew and Out-of-Order Events
**Interviewer:** "An endpoint's local clock is messed up and is set to the year 2015. Another endpoint goes offline, buffers its events for 2 days, and then sends them. How does your rule engine handle this?"

**The Trap:** Using the "Event Time" (the timestamp generated by the agent) for stream processing windows will break. The 2015 event will either be dropped or mess up historical aggregations.

**The Solution:**
*   **Ingestion Time vs. Event Time:** For real-time anomaly detection, rely on **Ingestion Time** (the time the API Gateway received the payload) or apply **Watermarks** in Flink that allow for a bounded lateness (e.g., accept events up to 5 minutes late).
*   Events that are wildly out of bounds (e.g., > 1 hour old) should be routed to a "Dead Letter Queue" (DLQ) for forensic storage but excluded from real-time alerting to prevent false positives.

## 4. Alert Fatigue & Deduplication
**Interviewer:** "An agent detects its disk space is at 5%. It sends a telemetry event every 10 seconds. Your system processes it perfectly. The customer's PagerDuty goes off 360 times an hour for a single laptop. They cancel their SentinelOne contract. How do you fix this?"

**The Trap:** Not having a stateful alerting tier.

**The Solution:**
*   The Alerting Service (Python/Go) must maintain a cache (Redis) of recently fired alerts.
*   Implement a **Cooldown Period / Debounce**. 
*   **Flow:** 
    1. Anomaly received.
    2. Check Redis for key `alert:{tenant_id}:{agent_id}:low_disk`.
    3. If exists, drop or aggregate the alert.
    4. If not, trigger PagerDuty and set Redis key with a TTL of 4 hours.

## 5. Handling System Updates (The Managerial Question)
**Interviewer:** "You are rolling out a new rule: 'Alert if Agent Version < 23.1'. How do you deploy this without triggering 2 million alerts globally instantly?"

**The Solution (Process & Architecture):**
*   **Dark Launching / Shadow Mode:** Deploy the rule in a "shadow" mode where it evaluates data and logs to a dashboard but does *not* publish to the Alerting Kafka topic.
*   **Gradual Rollout:** Enable the rule on a per-tenant basis using Feature Flags (e.g., LaunchDarkly). Start with internal SentinelOne dogfooding -> Beta Customers -> GA.
*   **Remediation Workflows:** Instead of just alerting, the system should trigger an automated workflow (e.g., telling the agent to auto-update via a control plane command).
